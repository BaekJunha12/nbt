# 3인 역할 분담 및 작업 순서 (DB 없이, Seed 데이터 방식)

> 이름은 편의상 A/B/C로 표기했습니다. 실제로는 각자 강점에 맞춰 이름만 바꿔서 배정하시면 됩니다.
> **전제**: DB 없이, 고정된 Seed 유저 데이터(JSON)를 코드에 포함시켜 클라이언트(브라우저)에서 바로 계산하는 구조로 진행합니다. 서버/API 자체가 필요 없어져서 통합 과정이 훨씬 단순해집니다.

---

## 역할 구성

| 담당 | 역할 | 핵심 책임 |
|---|---|---|
| **A** | 매칭 알고리즘 | Hard 필터 + Soft 점수 계산 + 가중치 계산을 하는 순수 함수 구현 |
| **B** | 입력 폼 | 프로필/희망조건/생활패턴/우선순위 입력 UI, 입력값을 알고리즘이 기대하는 형태로 가공 |
| **C** | Seed 데이터 + 결과 화면 | 가상 유저 JSON 작성, 추천 리스트/상세 궁합 화면 UI |

**DB가 없어지면서 달라진 점**
- 서버 세팅, 스키마 설계, API 명세가 통째로 사라짐
- A가 만드는 건 API가 아니라 **그냥 하나의 JS 함수** (`getMatches(myInput, priorities, seedUsers)` 같은 형태)
- B, C, A 세 사람의 결과물은 결국 "함수 호출"로 연결되는 것뿐이라, 통합 단계가 훨씬 가벼워짐

---

## Phase 0 — 킥오프 (전원 함께, 30분 이내)

DB/API 논의가 사라진 대신, 이것만 맞추면 됩니다.

- [ ] **입력 객체 형태 합의** — 예:
  ```js
  {
    gender: "male", ageRange: [20,24],
    smoking: "non_smoker", smokingTolerance: 3,
    outing: [8.5, 9.5], return: [18, 21], sleep: [23, 1],
    social: 4, noise: 5,
    priorities: ["noise", "sleep", "social"]  // 1~3순위
  }
  ```
- [ ] **유저(Seed) 객체 형태 합의** — 입력 객체와 동일한 필드 구조 사용 (일관성 유지)
- [ ] **출력(매칭 결과) 형태 합의** — 예:
  ```js
  [{ userId, finalScore, breakdown: { noise: 80, sleep: 60, ... } }]
  ```

이 세 가지 "형태"만 미리 합의되면 A/B/C가 서로 안 만나도 각자 작업이 가능합니다.

---

## Phase 1 — 병렬 작업 (동시 진행, DB 대기 없이 바로 시작 가능)

### A. 매칭 알고리즘
- [ ] Hard 필터 함수 (성별, 나이, 흡연 0점)
- [ ] Soft 점수 함수들 (흡연 MIN결합 / 외출·귀가·취침 중심값+겹침 / 취침 정오시프트 / 교류·소음 diff)
- [ ] 가중치 정규화 + 최종 점수 계산 함수
- [ ] **본인이 직접 만든 더미 유저 2~3명으로 단위 테스트** (C의 Seed 데이터를 기다릴 필요 없음 — 형태만 맞으면 됨)

### B. 입력 폼
- [ ] 프로필/희망조건 입력 UI
- [ ] 생활패턴(외출/귀가/취침) 시간 범위 입력 UI
- [ ] 우선순위 1~3위 선택 UI
- [ ] 제출 시 Phase 0에서 합의한 입력 객체 형태로 콘솔 출력까지만 (아직 A 함수 호출 X)

### C. Seed 데이터 + 결과 화면
- [ ] 가상 유저 10~20명 JSON 작성 (극단 케이스 포함: 하드필터 걸리는 사람, 경계값 나이 등)
- [ ] 추천 리스트 화면 UI (더미 결과 배열로 퍼블리싱)
- [ ] 상세 궁합 화면 UI (점수 + 항목별 이유/주의사항 레이아웃)

---

## Phase 2 — 통합 (DB/API 단계가 없어서 여기가 제일 짧아짐)

- [ ] B의 입력 폼 제출 → A의 알고리즘 함수를 직접 호출 (같은 프론트엔드 코드 안에서 함수 import)
- [ ] A의 함수에 C가 만든 Seed 데이터를 인자로 전달
- [ ] A의 함수 결과(배열)를 C의 결과 화면 컴포넌트에 그대로 props로 전달
- [ ] 셋이 짧게 모여서 실제 값 흘려보내며 화면 확인

---

## Phase 3 — 테스트 & 마무리

- [ ] 실제 흐름 E2E 확인: 입력 → 계산 → 결과 화면
- [ ] 극단 케이스 점검 (하드필터로 후보 0명 남는 경우 예외처리)
- [ ] 데모 시나리오 대본 준비 (어떤 입력값 넣을지, 어떤 Seed 유저가 매칭되는지 미리 정하기)
- [ ] 시간 남으면: 개인화 가중치 UI 고도화, 집 추천 등 착수

---

## 진행 중 막힐 수 있는 지점

- B가 만드는 입력 객체 필드명과 A가 기대하는 필드명이 미묘하게 다를 수 있음 → Phase 0에서 합의한 형태를 문서/코드 주석으로 박아두고 그대로 따르기
- C의 Seed 데이터가 실제로 다양한 케이스(겹침 있음/없음, 하드필터 걸림 등)를 포함 안 하면 데모가 밋밋해짐 → 극단 케이스 몇 개는 의도적으로 섞기
- 미확정 항목(교류/소음 점수 단위, 거주기간/예산 처리 방식)은 A가 Phase 1 시작 전에 빠르게 결정하고 시작하는 게 좋음
